## What blocks this function

The residual is wholly in .rdata size, not in instruction shape. Every one of the 40 differing words is exactly `+0x20` on a `.data`/`.bss` lo16 immediate; the decoded instruction text and relocation equations are *identical*. The 32 bytes (20 + 12 pad) come from the compiler's 5-word jump table (label addresses) in `.rdata`.

The target's `.rdata` layout is:

```
[0x000..0x1B0)  bios.c's own string literals    (432 bytes)
[0x1B0..0x1C4)  jump table: 5 code addresses     ( 20 bytes)
[0x1C4..0x260)  CD_sync/CD_ready/CD_cw/CD_init/CD_datasync strings  (156 bytes)
```

In the harness's TU model, the member's entire rodata is one generated asm part
(`_data.c` → `INCLUDE_ASM __library_member_data` → 608-byte `.include` of the
extracted object's `.rdata`). The compiler emits static data (including either a
`switch` jump table or a `static const void *keep[]` label table) **in source
order right after the containing part**. So the table always lands at `.rdata+608`, never at 432.

A `switch` (exp6: 303/345) gives the same residual as a computed-goto with
`keep[]` (exp7: 305/345): the extra 20 bytes of `.rdata` shift every following
section by 0x20 and every `.data`/`.bss` relocation with it. Section tricks
(`psyq-lnk` accepts only 6 section names; unknown → error, non-empty known →
emits record + bytes) and harness TU-splitting (`validateLibraryTu` rejects a
second data part) have both been measured and confirmed closed.

## What a human needs to decide

There are two routes to unblock, both require a human decision:

**Route A — Harness change.** Allow the TU manifest to split the generated
data part into two fragments, e.g. by declaring a section range on a part or
by allowing a second generated-data symbol. This would let `_data.c` contain
only `.rdata` [0..432] + `.data` + `.bss`, with a separate suffix part for
the trailing string literals, placing the compiler-emitted table exactly at
432. A harness-owner decision.

**Route B — Shared-data authorisation.** Remove the trailing 156 bytes
of `.rdata` from the extracted `__library_member_data.s` by hand (splitting
the generated assembly), and re-author those bytes as C string-literal
definitions in a shared `.h` part placed after `func_00000090.c` in the TU.
The compiler would then emit the strings at the right position. This edits
shared storage that `_data.c`'s include is the sole source of truth for,
and the symbol-table differences from compiler-generated names would need
verification. A code-owner decision.

**Route C — Decompile the owner functions first.** The trailing 156 bytes are
string literals owned by `CD_sync`, `CD_ready`, `CD_cw`, `CD_init` and
`CD_datasync`. If those functions were decompiled to C, their string literals
would be compiler-emitted (in source/part order, right after this function's
jump table) and `_data.c` could shrink to 0..432. This is the most natural
resolution but depends on those five functions being matched first — each of
which is currently an `INCLUDE_ASM` stub.
